--------------------------------------------------------------------------------
PROJECT OVERVIEW
--------------------------------------------------------------------------------
MFT (Managed File Transfer) Platform — Lifetime License at $999 USD.
Landing page collects leads, processes payments via Stripe, records customers
in Frappe CRM, and syncs billing to ERPNext.

Stack:
  - Frontend  : HTML/CSS/JS (index.html, style.css, main.js)
  - Backend   : Node.js + Express (server.js)
  - Payment   : Stripe Checkout (hosted payment page)
  - CRM       : Frappe CRM (self-hosted via WSL Ubuntu 22.04)
  - Billing   : ERPNext (self-hosted, same Frappe bench)
  - Email     : SMTP via hephzibahtech.com mail server

--------------------------------------------------------------------------------
COMPLETED WORK
--------------------------------------------------------------------------------

[1] LANDING PAGE SERVER (server.js)
------------------------------------
- Built Express server on port 7000 (configurable via .env PORT)
- CORS configured with allowed origin (configurable via ALLOWED_ORIGIN)
- Security headers: HSTS, X-Content-Type-Options, X-Frame-Options, X-XSS-Protection, Referrer-Policy
- Static file serving for HTML/CSS/JS assets
- BASE_PATH support for reverse proxy / subpath deployment
- In-memory session store (Map) to track Stripe checkout sessions
- /api/session-details/:sessionId endpoint for success page to retrieve payment data
  - Checks in-memory store first (fast path)
  - Falls back to Stripe API if server was restarted
  - Triggers processERPNext() on first access (fire-and-forget, non-blocking)
  - On Stripe fallback: calls processERPNextDirect() (awaited, enriches response)

[2] STRIPE PAYMENT INTEGRATION (routes/checkout.js)
-----------------------------------------------------
- POST /api/create-checkout-session
  - Accepts: { name, org, email } from the landing page form
  - Validates required fields (name, org, email)
  - Generates a sequential bill number (MFTBILL-00001, MFTBILL-00002, ...)
  - Creates a Stripe Checkout Session:
      Product : MFT Platform — Lifetime License
      Price   : $999.00 USD (unit_amount: 99900)
      Mode    : payment (one-time, not subscription)
      Metadata: billNumber, customerName, organization
  - Stores session data in in-memory sessionStore
  - Returns Stripe hosted checkout URL to frontend
- Bill counter persisted in bill-counter.json (survives server restarts)
  - Format: MFTBILL-XXXXX (zero-padded 5 digits)
- Success URL: /success.html?session_id={CHECKOUT_SESSION_ID}
- Cancel URL : /cancel.html

[3] BILL NUMBER COUNTER (utils/store.js)
-----------------------------------------
- Persistent counter stored in bill-counter.json
- nextBillNumber() reads, increments, and writes atomically
- Format: MFTBILL-00001, MFTBILL-00002, ...
- sessionStore (Map) holds active sessions keyed by Stripe session ID

[4] ERPNEXT FULL PAYMENT AUTOMATION (server.js -> processERPNext)
-----------------------------------------------------------------
- Replaces old pushToFrappe() Lead-only push
- Calls ERPNext API: erpnext.accounts.doctype.mft_license.mft_license.process_payment (via POST)
- Triggered fire-and-forget when success page first loaded
- ERPNext creates (in order):
    1. Customer     - found by email (deduped) or created new
    2. Sales Invoice - MFT-LIFETIME, qty=1, fetched price from ERPNext
    3. Payment Entry - linked to invoice, reference_no = Stripe session ID
    4. MFT License  - unique license key, stored in ERPNext custom DocType
- Idempotent: same Stripe session ID never creates duplicate records
- Enriches sessionStore with: invoiceNumber, licenseKey, itemName, amount, purchaseDate
- Auth: HTTP Basic with API key + API secret (Base64 encoded)

[5] CONTACT FORM (routes/contact.js)
--------------------------------------
- POST /api/contact
- Accepts: { name, email, countryCode, mobile, message }
- Validates: name (required, <=100 chars), email (regex), message (10-2000 chars)
- Sends styled HTML + plain text email via SMTP (nodemailer)
- Reply-To set to the submitter's email
- SMTP config: hephzibahtech.com mail server, port 587

[6] EMAIL TEMPLATES (templates/contactEmail.js, utils/mailer.js)

- Plain-text fallback
- Nodemailer transporter configured from env (SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS)

[8] SUCCESS PAGE (success.html)
--------------------------------
- Displays 12 fields in exact order after successful Stripe payment:
    1.  Payment Status       - "Paid" (shown in header badge)
    2.  Invoice Number       - ERPNext Sales Invoice number (e.g. ACC-SINV-0001)
    3.  Payment Reference ID - Stripe Session ID (cs_test_xxx...)
    4.  Purchase Date        - from ERPNext, formatted DD Mon YYYY
    5.  Customer Name        - from session / Stripe
    6.  Organization         - from session / Stripe metadata
    7.  Email                - from session / Stripe
    8.  Product Name         - fetched dynamically from ERPNext Item master
    9.  Subscription Type    - "Single Purchase" (hardcoded, future: plans)
    10. Amount Paid          - fetched dynamically from ERPNext Item Price ($999.00 USD)

- Polling: retries every 2 seconds (up to 10x) until license key arrives from ERPNext
- cancel.html: shown when user abandons Stripe checkout

DocType: MFT License (tabMFT License in MariaDB - VERIFIED)
  Fields:
    - license_key         (Data, UNIQUE, required)    - MFT-LIFE-XXXX-XXXX-YYYY
    - status              (Select: Active/Revoked/Expired)
    - customer            (Link -> Customer)
    - email               (Data, Email, indexed)
    - invoice_number      (Link -> Sales Invoice, indexed)
    - stripe_session_id   (Data, UNIQUE, "Payment Reference ID", indexed)
    - product             (Link -> Item)
    - purchase_date       (Date)
    - expiry              (Date)
    - amount_paid         (Currency)

API Endpoint: POST /api/method/erpnext.accounts.doctype.mft_license.mft_license.process_payment
  Params  : stripe_session_id, name, org, email, bill_number
  Returns : invoice_number, license_key, item_name, amount, purchase_date, status
  Logic   :
    1. Idempotency check - if session already processed, return existing data
    2. Fetch item name + price from ERPNext Item master (MFT-LIFETIME)
    3. Find customer by email (Contact Email) OR create new Customer + Contact
    4. Create + submit Sales Invoice (MFT-LIFETIME, price from ERPNext)
    5. Create + submit Payment Entry (reference_no = stripe_session_id)
    6. Generate unique license key (MFT-LIFE-XXXX-XXXX-YEAR)
    7. Insert MFT License record
    8. Return all data to landing page

Duplicate Prevention:
  - Customer    : checked by email via Contact Email doctype (not name/org)
  - Payment     : checked by stripe_session_id uniqueness in MFT License
  - License Key : UNIQUE constraint in ERPNext + generation loop

[F] FULL ARCHITECTURE (CURRENT — 2026-05-27)
----------------------------------------------

  Total Architecture:
    Next.js Landing Page (port 7000)
           ↓
    Stripe Payment (hosted checkout)
           ↓
    Express Backend API (port 5010)
           ↓
    ERPNext / Frappe (port 8000)
           ↓
    Generate License Key → Store in MFT License DocType
           ↓
    Return to success page

  Detailed Payment Flow:
    1. Customer visits localhost:7000 (Next.js landing page)
    2. Fills in Name, Email, Organization → clicks "Pay Now"
    3. POST /api/create-checkout-session → Next.js proxies to Express :5010
    4. Express creates Stripe Checkout Session (metadata: billNumber, name, org)
    5. User redirected to Stripe hosted checkout → completes payment
    6. Stripe redirects to /success?session_id=cs_test_xxx
    7. Success page polls GET /api/session-details/:sessionId (up to 10x, every 2s)
    8. Next.js proxies to Express GET /mft/session-details/:sessionId
    9. Express returns cached session data + fires processMftERPNext() in background
    10. processMftERPNext() calls Frappe API (token auth):
          POST /api/method/mft_integration.api.process_payment
    11. Frappe api.process_payment():
          a. Idempotency check (stripe_session_id unique in MFT License)
          b. Find/create Customer (deduped by email via Contact Email)
          c. Create + Submit Sales Invoice (MFT-LIFETIME, $999 USD)
          d. Create + Submit Payment Entry (ref = stripe_session_id)
          e. Generate unique license key (MFT-LIFE-XXXX-XXXX-YYYY loop)
          f. Insert MFT License record (status = Active)
          g. Return: invoice_number, license_key, item_name, amount, purchase_date
    12. Express updates mftSessionStore with ERP data
    13. Next poll returns full data → success page displays:
          Invoice Number, License Key, Payment Reference ID,
          Purchase Date, Customer Name, Org, Email,
          Product Name, Amount ($999 USD), Mode of Payment

--------------------------------------------------------------------------------
BEFORE — HOW EMAIL WAS SENT (Express)
--------------------------------------------------------------------------------

  Stripe Payment Confirmed
        ↓
  Express: GET /mft/session-details/:sessionId
        ↓
  Express calls Frappe API → process_payment()
        ↓
  Frappe returns: { license_key, invoice_number, amount, ... }
        ↓
  Express calls emailService.sendLicenseEmail()   ← Nodemailer / SMTP directly
        ↓
  Email sent from Express server

  Problems:
  - Two systems managing the same email — hard to debug
  - If Express crashes after payment but before email → license lost with no email
  - No retry on failure
  - No visibility in Frappe logs

--------------------------------------------------------------------------------
AFTER — HOW EMAIL IS SENT NOW (Frappe)
--------------------------------------------------------------------------------

  Stripe Payment Confirmed
        ↓
  Express: GET /mft/session-details/:sessionId
        ↓
  Express calls Frappe API → process_payment()
        ↓
  Inside process_payment() in Frappe:
    1. Creates Sales Invoice → submits
    2. Creates Payment Entry → submits
    3. Generates license key
    4. Inserts MFT License record
    5. frappe.db.commit()
    6. frappe.sendmail(now=False)  ← queues email in tabEmail Queue
        ↓
  Frappe returns: { license_key, invoice_number, ... }
        ↓
  Express just logs: "✓ Processed — license email sent by Frappe"

--------------------------------------------------------------------------------
FRAPPE EMAIL SCHEDULER FLOW (DETAILED)
--------------------------------------------------------------------------------

  frappe.sendmail(now=False) called
        ↓
  Frappe creates record in tabEmail Queue
    - status      = "Not Sent"
    - recipients  = customer email
    - subject     = "Your MFT License Key — Hephzibah Technologies"
    - message     = full branded HTML
        ↓
  frappe.db auto-commits when API call finishes
        ↓
  Background: Frappe Scheduler runs every ~1 min
        ↓
  Worker runs: frappe.email.queue.flush
        ↓
  Picks up all "Not Sent" records from Email Queue
        ↓
  Opens SMTP connection to mail.hephzibahtech.com
  using "Paul support mail" Email Account (configured in Frappe UI)
        ↓
  Sends email via SMTP
        ↓
    Success → status = "Sent"
    Failure → keeps "Not Sent", logs error, retries next flush cycle automatically
        ↓
  Frappe auto-deletes Sent records after 30 days

    Fix:   Changed to now=False — queue worker manages connection properly

TOPIC 1 — COMPLETE OPTION C PICTURE (Finalized & Documented)

  Option C = ERPNext Native Subscriptions + Stripe Payment Request.

  MONTH 1 — Initial Purchase:
  -----------------------------------------------------------------------
    Website -> Stripe -> Express -> Frappe

    Records created in ERPNext:
      1. Customer          — found by email (deduped) OR created new
      2. Sales Invoice     — status: Paid, item: MFT-MONTHLY, amount: $9
      3. Payment Entry     — status: Submitted, reference: Stripe session ID
      4. Subscription      — links Customer to MFT Monthly Plan, billing_date = today+30
      5. MFT License       — license_key: MFT-LIFE-XXXX-XXXX-2026
                             status: Active
                             plan: Monthly
                             expiry: purchase_date + 30 days
    License email sent by Frappe (via frappe.sendmail) — key + expiry + access link.
    License key NOT shown on success page — email delivery only.

  MONTH 2+ — Recurring Renewal:
  -----------------------------------------------------------------------
    ERPNext scheduler fires on billing date (every 30 days for Monthly)
      -> Auto-creates Sales Invoice (status: Unpaid, $9.00)
      -> ERPNext sends Payment Request email to customer:
           "Your MFT Monthly license renewal is due — [Pay Now $9]"

    Customer clicks Pay Now link
      -> Stripe Checkout page (mode: payment)
      -> Pays $9

    Stripe webhook -> Express backend -> Frappe extend_license()
      -> Finds existing Active MFT License for this email + plan
      -> EXTENDS expiry: old_expiry + 30 days   <-- SAME KEY, new expiry
      -> Marks Sales Invoice as Paid
      -> Creates Payment Entry (Submitted)
      -> Queues renewal confirmation email:
           "License renewed until [new date]. Your key MFT-LIFE-XXXX is unchanged."

    KEY RULE: Month 2+ NEVER creates a new license key.
              The existing license key is extended in-place.
              Customer uses the same key in MFT app with no changes.

  MFT APP — License Validation (any time):
  -----------------------------------------------------------------------
    Customer opens MFT Application -> enters email + license key
    MFT app calls ERPNext API:
      GET /api/method/mft_license.validate_license?email=xxx&license_key=xxx

    ERPNext checks:
      expiry is blank (Lifetime)      -> valid: true  (full access)
      expiry >= today                 -> valid: true  (access granted)
      expiry < today                  -> valid: false (expired, redirect to purchase)
      no active license found         -> valid: false (no license)
      status = Revoked                -> valid: false (contact support)

    MFT app NEVER talks to Stripe directly — ERPNext is the single source of truth.
    Optional: show renewal banner if expiry <= 14 days away.

TOPIC 2 — DUAL-LAYER DUPLICATE PURCHASE PREVENTION (Design Finalized)
--------------------------------------------------------------------------------

  Edge case: Customer forgets they have an active Monthly license and buys again
  with the same email -> would create 2 active licenses + waste $9.
  Solution: Two-layer defense system documented in Section 11 of the Word doc.

  LAYER 1 — Frontend Pre-Payment Check (BEFORE Stripe charges):
  -----------------------------------------------------------------------
    When customer clicks Pay Now:
      POST /api/check-active-license { email, plan }
      Express queries ERPNext: active MFT License for this email + plan?

      CASE A — No active license found:
        -> Proceed normally to Stripe checkout (intent = "new")

      CASE B — Active license found (not expired):
        -> Show warning modal on landing page:
             "Active License Found
              You already have a Monthly license valid until 03 Jul 2026.
              Purchasing again will EXTEND your existing license by 30 more days.
              Amount: $9.00
              [Cancel]   [Yes, Extend My License ->]"

        -> If Cancel  : close modal, no Stripe redirect, no charge, stay on page
        -> If Confirm : proceed to Stripe with intent = "extend"

  LAYER 2 — Frappe Post-Payment Safety Net (AFTER Stripe payment):
  -----------------------------------------------------------------------
    Inside process_payment() in mft_license.py — runs after idempotency check:

    Check: does Active MFT License exist for same email + same plan?

    If FOUND (duplicate purchase):
      -> EXTEND expiry + 30 days (Monthly) / + 365 days (Yearly)
      -> Do NOT create new MFT License record
      -> Sales Invoice + Payment Entry still created (accounting stays clean)
      -> Email: "License extended until [new date]. Same key: MFT-LIFE-XXXX"

    If NOT FOUND:
      -> Normal flow: create new MFT License record

  WHY TWO LAYERS?
  -----------------------------------------------------------------------
    Layer 1 prevents the problem before it happens (better UX, no wasted money).
    Layer 2 is the safety net — catches duplicates even if Layer 1 was skipped.
    Together = defense-in-depth. No duplicate license ever created.

  FOUR SCENARIOS COVERED:
  -----------------------------------------------------------------------
    Scenario A: No active license       -> Normal purchase -> New license created
    Scenario B: Active + Cancel         -> No charge, no change, stays on page
    Scenario C: Active + Extend         -> Stripe charge -> Layer 2 extends expiry
    Scenario D: Layer 1 bypassed        -> Stripe charge -> Layer 2 catches, extends

  EDGE CASE — Different Plan (Upgrade):
  -----------------------------------------------------------------------
    Monthly user buys Yearly:
      -> check_active_license(email, plan="Yearly") -> no Yearly license found
      -> No warning shown (different plan = upgrade, not duplicate)
      -> New Yearly license created
      -> Old Monthly license marked Superseded

  KEY BUSINESS RULES:
  -----------------------------------------------------------------------
    Same email + same plan + active  -> EXTEND (Layer 1 warns, Layer 2 enforces)
    Same email + different plan      -> NEW license (upgrade path, Layer 1 not triggered)
    Same email + no active license   -> NEW license (normal purchase)
    Same Stripe session ID again     -> Return existing data (idempotency, no new records)

[EDGE CASE 1] — PLAN UPGRADE: Monthly Customer Buys Yearly
------------------------------------------------------------------------

  Scenario:
    Customer has active Monthly license (expiry: 03 Jul 2026).
    Forgets or decides to upgrade — goes to website and buys Yearly
    using the same email address.

  Problem Without Handling:
    check_active_license(email, plan="Yearly") → no Yearly license found
    → No warning shown → customer proceeds to Stripe → pays $99
    → process_payment() creates NEW Yearly MFT License
    → Customer now has 2 active licenses (Monthly + Yearly)
    → Monthly subscription days WASTED (already paid for until Jul 3)

  Correct Handling — Upgrade Flow:
    Layer 1 check: check_ANY_active_license(email) → finds Monthly license
    → Show UPGRADE warning modal (different from duplicate modal):
        "Active Monthly License Found
         Valid until: 03 Jul 2026
         Upgrading to Yearly will extend your access by 365 days
         from your current expiry date.
         New expiry after upgrade: 03 Jul 2027
         Amount: $99.00
         [Cancel]   [Yes, Upgrade to Yearly →]"

    Layer 2 — Frappe process_payment() on confirmation:
      → Finds existing Active Monthly MFT License for this email
      → UPDATES existing MFT License record (NOT a new record):
          product : MFT-MONTHLY → MFT-YEARLY   (update plan/product)
          expiry  : 03 Jul 2026 → 03 Jul 2027  (extend +365 days FROM current expiry)
          status  : Active (unchanged)
          license_key: MFT-LIFE-XXXX-XXXX-2026 (UNCHANGED — same key)
      → Creates new Sales Invoice (item: MFT-YEARLY, $99) → Paid
      → Creates new Payment Entry (Submitted)
      → Queues upgrade confirmation email:
          "Upgraded to Yearly. License valid until 03 Jul 2027.
           Your key MFT-LIFE-XXXX is unchanged — no change needed in MFT app."

  KEY CORRECTION — "12 months" vs "365 days":
    User said: "extend 12 months extra"
    Correct:   extend 365 days (not calendar months — precise and consistent in code)
    Code:      new_expiry = add_days(existing_expiry, 365)

  KEY RULE — Extend FROM current expiry (not from today):
    Customer bought Monthly Jun 1 (expiry Jul 1). Upgrades on Jun 15 (16 days left).
    Extend from Jul 1:  new expiry = Jul 1 + 365 = Jul 1, 2027  ← CORRECT (keeps paid days)
    Extend from today:  new expiry = Jun 15 + 365 = Jun 15, 2027 ← WRONG (loses 16 days)

  IMPORTANT — Product field also updated:
    When upgrading Monthly → Yearly, TWO fields must change on MFT License:
      1. product (Item Code): MFT-MONTHLY → MFT-YEARLY
      2. expiry:              old_expiry   → old_expiry + 365 days
    NOT updating the product field would leave the record saying "Monthly"
    but with a 365-day expiry — confusing for ERPNext admins.


[EDGE CASE 2] — plan FIELD CLARIFICATION: What Is It Actually?

  Question raised: Does plan: Monthly refer to the Item Price ID from ERPNext?

  Answer: NO. Clarification of what each ERPNext field is:

  Item DocType (Stock → Item):

    Item Name  : MFT Platform Monthly License
    Item Group : SaaS Products

  Item Price DocType (Stock → Item Price):
    item_code  : MFT-MONTHLY          ← links to Item
    price_list : MFT Selling (USD)    ← our price list
    rate       : 9.00                 ← the actual price
    name       : auto-generated ID    ← never used directly in code

  MFT License DocType — existing field:
    product    : Link → Item          ← stores MFT-MONTHLY / MFT-YEARLY / MFT-LIFETIME

  Conclusion:
    "plan" = the product field (Link to Item, stores item_code like MFT-MONTHLY)
    We do NOT need to add a separate Plan field —
    the existing product field already carries the plan information.
    In code: if license.product == "MFT-MONTHLY" → monthly plan → 30 days
             if license.product == "MFT-YEARLY"  → yearly plan  → 365 days
             if license.product == "MFT-LIFETIME"→ lifetime     → no expiry

[IMPORTANT CONSIDERATION 2] — RATE FETCH PATH IN process_payment()
------------------------------------------------------------------------

  The rate used for Stripe checkout session + Sales Invoice is fetched from
  ERPNext Item Price DocType using item_code as the lookup key.

  Frappe code pattern:
    item_price = frappe.db.get_value(
        "Item Price",
        filters={
            "item_code": item_code,      # MFT-MONTHLY / MFT-YEARLY / MFT-LIFETIME
            "price_list": "MFT Selling"
        },
        fieldname=["price_list_rate", "item_name"],
        as_dict=True
    )
    rate = item_price.price_list_rate   # 9.00 / 99.00 / 999.00

  This means:
    - Stripe session unit_amount = rate * 100 (cents) → fetched from ERPNext
    - Sales Invoice rate = same Item Price rate
    - Both always in sync — no mismatch possible

HOW IT WORKS — daily timeline for a Monthly customer who doesn't renew:
  Jun 1  — License expires (expiry date)
  Jun 1  — Grace period starts (7 days to pay)
  Jun 8  — grace_period_expiry passes
  Jun 9  — auto_expire_licenses() runs → status = Expired
  Jun 9  — Customer tries to buy again → check_active_license() returns has_active=False
           → no warning modal → fresh purchase → new license record created

WHY GRACE PERIOD IS USED (not expiry):
  We intentionally check grace_period_expiry < today (not expiry < today).
  This gives the customer their full 7-day payment grace period.
  Licenses with expiry=null (Lifetime) have grace_period_expiry=null
  and are excluded from the query automatically by Frappe db filters.

IMPACT ON OTHER FLOWS:
  check_active_license() (Layer 1 duplicate check):
    Filters by status="Active" — expired licenses automatically excluded ✓
  _check_and_extend_existing() (Layer 2 post-payment extension):
